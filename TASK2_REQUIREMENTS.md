# TASK2_REQUIREMENTS.md — Восстановленные функциональные требования

## Функциональные требования

### Управление акциями (Web UI)

**ФТ-01.** Система отображает список всех акций, хранящихся в базе данных, отсортированных по наименованию компании в алфавитном порядке.  
_Источник:_ `dashboard/views.py` → `ShareListView`, `ordering = ["name"]`

**ФТ-02.** Список акций отображается с постраничной навигацией: на одной странице отображается не более 100 записей.  
_Источник:_ `dashboard/views.py` → `ShareListView`, `paginate_by = 100`

**ФТ-03.** Система отображает детальную страницу акции, включающую её атрибуты и интерактивный график изменения цены за последние 180 дней с дневным интервалом.  
_Источник:_ `dashboard/views.py` → `ShareDetailView`; `dashboard/services/graph.py`

**ФТ-04.** График цены строится на основе данных о дневных свечах (daily candles), полученных из Tinkoff Invest API. Отображается цена закрытия (`close.units`) в виде линейного графика.  
_Источник:_ `dashboard/services/graph.py`

**ФТ-05.** Аутентифицированный пользователь может вручную добавить новую акцию в систему через веб-форму.  
_Источник:_ `dashboard/views.py` → `ShareCreateView`; `dashboard/forms.py`

**ФТ-06.** Аутентифицированный пользователь может отредактировать атрибуты существующей акции через веб-форму.  
_Источник:_ `dashboard/views.py` → `ShareUpdateView`

**ФТ-07.** Аутентифицированный пользователь может удалить акцию из системы с предварительным подтверждением.  
_Источник:_ `dashboard/views.py` → `ShareDeleteView`; `dashboard/templates/dashboard/delete.html`

**ФТ-08.** Неаутентифицированный пользователь перенаправляется на главную страницу при попытке выполнить операции создания, редактирования или удаления акций.  
_Источник:_ `dashboard/views.py` → `IsUserAuthenticatedMixin.handle_no_permission()`

### Автоматическое обновление рыночных данных

**ФТ-09.** Система автоматически обновляет текущую рыночную цену каждой акции, периодически запрашивая данные через Tinkoff Invest API.  
_Источник:_ `dashboard/tasks.py` → `update_last_price`; `config/celery.py`

**ФТ-10.** После каждого обновления цены система определяет направление ценового тренда: если новая цена выше предыдущей — флаг `is_trend_high` устанавливается в `True`, иначе в `False`.  
_Источник:_ `dashboard/tasks.py` → логика сравнения `share.last_price > last_price`

**ФТ-11.** При ошибке получения данных для конкретной акции система продолжает обработку остальных акций, фиксируя ошибку в лог-файле.  
_Источник:_ `dashboard/tasks.py` → обёртка `try/except` с `logger.error(e)`

**ФТ-12.** Каждое успешное получение данных о цене акции фиксируется в системном логе с указанием идентификатора акции.  
_Источник:_ `dashboard/services/market_data.py` → `logger.info(f"Get last data for share with id {share.id}")`

### Первоначальная загрузка данных

**ФТ-13.** Система предоставляет management-команду `add_shares` для первоначальной загрузки списка всех доступных акций из Tinkoff Invest API в базу данных.  
_Источник:_ `dashboard/management/commands/add_shares.py`

**ФТ-14.** При загрузке акций через `add_shares` повторное выполнение команды не создаёт дублирующих записей (идемпотентная операция через `get_or_create`).  
_Источник:_ `dashboard/management/commands/add_shares.py` → `Share.objects.get_or_create(...)`

**ФТ-16.** REST API поддерживает фильтрацию акций по точному значению полей `name` и `ticker`.  
_Источник:_ `dashboard/api/v1/views.py` → `ShareFilter`, `filterset_class`

## Бизнес-правила и ограничения

- Поля `figi`, `ticker` и `uid` являются уникальными идентификаторами акции — дублирование недопустимо.
- Поля `last_price` и `is_trend_high` могут быть пустыми (`null`) — для новых акций, которые ещё не получили рыночные данные.
- Операции изменения данных в Web UI (создание, редактирование, удаление) требуют аутентификации.
- Источником рыночных данных является исключительно Tinkoff Invest API; для его использования требуется действующий API-токен (`TINKOFF_TOKEN`).
- Логирование событий ведётся одновременно в консоль и в файл `app.logs`.

## Основные сценарии использования

**Сценарий 1. Первоначальный запуск системы**
1. Запуск PostgreSQL (Docker).
2. Применение миграций: `python manage.py migrate`.
3. Загрузка акций: `python manage.py add_shares` — система запрашивает список инструментов из Tinkoff API и сохраняет их в БД.
4. Запуск Celery Worker и Celery Beat — система начинает периодически обновлять цены.
5. Запуск Django-сервера.

**Сценарий 2. Просмотр списка акций (анонимный пользователь)**
1. Пользователь открывает главную страницу (`/`).
2. Система отображает список акций, отсортированных по названию, с текущей ценой и индикатором тренда.

**Сценарий 3. Просмотр графика акции**
1. Пользователь нажимает на акцию в списке.
2. Система запрашивает исторические данные из Tinkoff API и отображает линейный график цен закрытия за 180 дней.

**Сценарий 4. Добавление акции вручную (авторизованный пользователь)**
1. Пользователь открывает страницу `/create`.
2. Заполняет форму со всеми атрибутами акции.
3. Система сохраняет запись и перенаправляет на главную страницу.

**Сценарий 5. Программный доступ к данным через REST API**
1. Клиент отправляет GET-запрос на `/api/v1/shares/` с параметрами фильтрации/поиска/сортировки.
2. Система возвращает JSON-ответ с постраничным списком акций.

## Выявленные неоднозначности, противоречия и дефекты реализации

**Д-01. Отсутствие аутентификации в REST API**  
`ShareViewSet` является `ModelViewSet` без каких-либо ограничений доступа. Любой анонимный пользователь может создавать, изменять и удалять акции через API. Является дефектом безопасности.

**Д-02. Некорректный редирект при отказе в доступе**  
`IsUserAuthenticatedMixin.handle_no_permission()` перенаправляет на `dashboard:index` (главную страницу), а не на страницу логина. Стандартное ожидаемое поведение — перенаправление на `/user/login/`.

**Д-03. Несоответствие названия Celery-задачи**  
Задача в расписании называется `"add-every-5-min"`, однако выполняется каждые 10 секунд (`"schedule": 10.0`). Название не отражает реальное поведение.

**Д-04. `auto_now=True` не обновляется через `.update()`**  
В `tasks.py` обновление цены выполняется через `Share.objects.filter(id=share.id).update(...)`. Поле `updated_at` с `auto_now=True` не обновляется при вызове `.update()` — только при `.save()`. В результате `updated_at` всегда содержит время последнего вызова `.save()`, а не время последнего обновления цены.

**Д-05. Некорректная обработка первичного обновления цены**  
В `tasks.py` при сравнении `share.last_price > last_price`, если `share.last_price` равен `None` (первое обновление), генерируется исключение. Оно перехватывается, и `is_trend_high` автоматически устанавливается в `True`, что является некорректным значением — направление тренда неизвестно.

**Д-06. Потеря дробной части цены**  
Цена в Tinkoff Invest API передаётся в виде двух полей: `units` (целые) и `nano` (миллиардные доли). В `market_data.py` и `graph.py` используется только `units`, что приводит к отображению неточных (округлённых до целых) цен.

**Д-07. `get_or_create` с несколькими полями в `add_shares`**  
Команда использует `get_or_create` со всеми полями в качестве условий поиска. Если хотя бы одно поле (например, `name`) изменится на стороне Tinkoff API, команда создаст дубликат вместо обновления записи.

**Д-08. `fields = "__all__"` в форме создания/редактирования акций**  
`ShareModelForm` открывает для ручного редактирования все поля модели, включая `last_price`, `is_trend_high` и `updated_at`, которые должны управляться только системой автоматически.

**Д-09. `SECRET_KEY` и `TINKOFF_TOKEN` хранятся в коде**  
Оба значения пустые строки, захардкоженные в `settings.py`. При реальном развёртывании это создаёт критическую угрозу безопасности.

**Д-10. `logger` инициализируется в `settings.py`**  
`logging.getLogger("main")` вызывается внутри модуля конфигурации. Это антипаттерн: логгер должен объявляться в модулях, которые его непосредственно используют.

**Д-11. `ShareDetailView` не обрабатывает несуществующий объект**  
`Share.objects.get(id=pk)` вызовет исключение `DoesNotExist`, если акция не найдена, что приведёт к необработанной ошибке 500 вместо корректного ответа 404.

**Д-12. `import *` в `dashboard/api/v1/router.py`**  
Использование `from .views import *` является плохой практикой — загрязняет пространство имён и скрывает реальные зависимости.
